## Plano data flow

```text
AeroAPI search / polling / callbacks     FAA NAS / signed advisory bridges
                         │                    │
                         └─────────┬──────────┘
                                   ▼
             Flight snapshot + track + inbound rotation + advisory context
                                   │
                                   ▼
             SQLite transaction: snapshot → typed events → push outbox
                         │                     │
                         ▼                     ▼
          Go HTTP API / share page      APNs and FCM HTTP v1
                         │                     │
                         ▼                     ▼
             Expo React Native UI        Native OS surfaces
```

- Flight IDs use provider identity when available. The schedule adapter retains synthetic schedule identity when a matching live record appears. Times use ISO 8601 on HTTP and epoch seconds for push. Departure-date search uses the origin's local date where known.
- Inbound history follows the same aircraft and airport sequence within a 25-hour window. Provider links can retain an inbound whose gate ETA slips past the onward schedule. Tail matches use movement order and stop at contradictory observed movement. The predictor uses the direct leg only. An unconfirmed inbound gate time expires when it passes or 30 minutes after observation, whichever comes first. Confirmed gate arrival and a reported wheels-on time have separate validity rules. Saved history remains available during a feed outage. An installation tracking the onward flight can open an uncached leg from that history. For a fresh airborne direct leg, the detail request can include up to 256 provider positions. A tail or takeoff change during the position request discards the old track. [FlightAware AeroAPI](https://www.flightaware.com/commercial/aeroapi/resources/aeroapi-openapi.yml) · [Flighty inbound tracking](https://flighty.com/help/where-is-my-plane)
- OOOI observations represent gate-out, wheels-off, wheels-on and gate-in separately. Status can also express boarding, cancellation and diversion. A later snapshot can revise an estimate. A previous observation cannot overwrite a newer snapshot.
- SQLite stores authenticated installations, tracked flights, share capabilities, device registrations and the push outbox. Device fanout and event writes share a transaction. A leased push job can be retried after a worker restart. Delivery is at least once, subject to expiry, provider policy and retry limits.
- User-visible changes include tail assignment, departure and arrival gate, baggage, significant ETD/ETA shifts, OOOI and matching advisories. Small ETA and ETD revisions accumulate against separate saved references so a series of minor updates can trigger an alert. Check-in is a 24-hour reminder with airline availability unverified. The operational departure estimate uses aircraft turnaround and applicable advisory constraints. Operators can train and deploy a local ridge-regression model from time-stamped observations. Its inputs, contributions and official flight times stay separate.
- Advisory-based forecasts expire at the earliest deadline of their evidence. An open-ended advisory can support a forecast for 30 minutes after observation. A dated advisory also honors its published end and a six-hour observation limit, with each forecast valid for up to 30 minutes. A material change in the current source revision retires a saved forecast until it can be recomputed. Learned explanations name current signals separately from the model's signed feature contributions.
- The outbox checks advisory and delay forecast evidence again before provider transport, including for older queued alerts. A published departure schedule change retires forecasts and alerts based on the previous schedule. Advisory program revisions share a provider collapse identity. [Aviation callbacks](docs/AVIATION_CALLBACKS.md)
- The optional METAR worker fetches small batches of public station observations for imminent tracked operations. The flight API returns recent adverse conditions separately from delay reasons, model inputs, and official airport advisories. [Aviation Weather Center data API](https://aviationweather.gov/data/api/)
- The signed advisory relay accepts documented FAA TFMData Flow Information airport ground stops and ground delay programs as XML. It preserves their source revision and operational window and routes relevant airport alerts through the outbox. Airport program definitions without flight membership stay out of delay estimates and training. [Aviation callbacks](docs/AVIATION_CALLBACKS.md#faa-tfmdata-airport-programs)
- Tracked flight details include recent airport notices from signed ingress and successful polling snapshots. A fresh, verified full departure closure can constrain the departure estimate after model inference. Simple daily UTC closures apply only during the matching occurrence, and the occurrence end caps forecast and alert freshness. Dispatch checks that the flight still falls within the queued window. [Aviation advisories](docs/AVIATION_CALLBACKS.md)
- A push message carries enough state to render the flight without an immediate API fetch. The push client enforces a 2 KiB request envelope. The internal Live Activity contract is `PlanoActivityAttributes` plus `flightId`, `flightNumber`, `status`, origin and destination codes, gate and terminal fields, optional seat, and departure, arrival and observation epochs.
- Flight alerts, Android live progress notifications and iOS Live Activities can open the corresponding flight. Connection alerts carry the inbound ID as well. The client validates both IDs and resolves them with a bounded tracked-flight lookup on the active installation. The tap carries no installation credential or server URL. [Expo Notifications](https://docs.expo.dev/versions/v56.0.0/sdk/notifications/) · [React Native Linking](https://reactnative.dev/docs/0.85/linking)
- The iOS Lock Screen and expanded Dynamic Island show gate, terminal, phase, and seat. Compact uses a system-rendered countdown when space allows. Minimal shows a phase icon. The display freshness window starts at the flight observation. An activity started from cached data can show an awaiting-update cue immediately. [WidgetKit dynamic dates](https://developer.apple.com/documentation/widgetkit/displaying-dynamic-dates)
- The iOS coordinator retries unfinished token uploads on foreground. It stops per-activity observation at the end of an activity and fences uploads when the server or installation credential changes. Slot-aware registration replaces the previous token for the same installation and activity in one SQLite transaction. [ActivityKit push notifications](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications)
- The iOS app stores a random ownership binding with its native registration. Local and remote starts include that binding in immutable ActivityKit attributes. The coordinator dismisses activities from a retired registration before it can upload their update tokens. A delayed push can appear briefly before the app wakes to dismiss it. [ActivityKit attributes](https://developer.apple.com/documentation/activitykit/activityattributes)
- iOS alert revocation persists an installation cutoff in SQLite. The app cancels token uploads before taking the cutoff and can retry a queued revocation against its original installation after a restart. Registration and cutoff checks share the device transaction.
- The default active-flight polling interval is 60 seconds. FlightAware callbacks can wake a durable targeted refresh for tracked flights and their explicitly linked direct inbound legs. An inbound callback updates the onward rotation and forecast with eligible cached advisories and keeps the onward observation timestamp. Signed bridge advisories can enqueue airport alerts directly. Outbox commits wake the dispatcher immediately, while a 200 ms fallback recovers ready retries. Provider acceptance, device arrival, end-to-end alert latency and behavior on specific onboard networks require separate measurement.
- Live Activity updates compare the current state with the last queued state for each device and flight. An unchanged observation renews the surface at most once a minute, even with faster polling. Reported flight progress keeps a long flight eligible when gate-out is unavailable.
- The dispatcher reserves capacity for each configured push provider when both are enabled. It rechecks each lease just before transport and caps the request deadline at the earlier of lease or message expiry. An outbox index narrows the ordering lookup to the same device and flight.
- An accepted flight observation retires queued state alerts when a gate or carousel changes, boarding ends, an estimate is withdrawn, or a departure prediction loses its evidence. The dispatcher checks the current flight phase again before submission, including for jobs created by older versions. Timeline entries and confirmed movement alerts stay available. Boarding pushes expire within 15 minutes of observation. Delivery of a push already accepted by APNs or FCM depends on the provider and device. [APNs delivery](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns) · [FCM delivery and collapse](https://firebase.google.com/docs/cloud-messaging/customize-messages/collapsible-message-types)
- iOS alerts that describe current flight state share an APNs collapse ID per installation, flight, and alert category. A newer revision waits while a request for that category is in flight. Other alert categories can send independently. Each revision carries its own event ID for notification taps, and factual movement alerts retain distinct notification IDs. APNs can reorder delivery after submission. [APNs delivery](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns)
- An optional AeroAPI reconciler registers departure-local route and day scopes for individually tracked flights. A separate opt-in adds verified direct inbound legs within the same quota. It stores an ownership marker before attempting creation, recovers ambiguous results by exact marker and scope, and verifies ownership before deleting a registration. [Aviation callbacks](docs/AVIATION_CALLBACKS.md)
- The Android app widget shows a single flight’s phase, progress, and estimated departure or arrival time in the device’s clock format. Compatible Android hosts can place it on the Lock Screen. A device-local opt-in adds the applicable gate, terminal, and seat from accepted live pushes. Turning that setting off clears those details from the widget cache. A widget tap carries a session-scoped opaque key. The native module resolves it only for the current, fresh selection before the app checks tracking with the active installation. The widget stores the routing ID in its private cache, which Android backup excludes. [Android lock-screen widget support](https://android-developers.googleblog.com/2025/03/widgets-on-lock-screen-faq.html)
- Android progress notifications and the widget use the same freshness and target rules. On Android 8 and later, the notification requests expiry at the earlier of the countdown target and observation deadline. Android 7 uses a static system timestamp. A redacted notification supplies phase and timing when Android hides private details. The private notification can stop both progress surfaces for that flight. A device-local ordering fence keeps delayed updates from reopening progress while ordinary tracking and alerts continue. [Android Live Updates](https://developer.android.com/develop/ui/views/notifications/live-update) · [Notification timeout](https://developer.android.com/reference/android/app/Notification.Builder#setTimeoutAfter(long))
- Android alerts carry the FCM expiry and ordinary flight events carry an observation revision. The app remembers recent revisions per flight and alert category in the private push session. A newer assignment replaces the visible alert for that category. Flight milestones can clear older state alerts while retaining their own notification identity. The current backend and Android app enable these checks together. [FCM delivery ordering](https://firebase.google.com/docs/cloud-messaging/customize-messages/collapsible-message-types) · [FCM message lifespan](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan)
- Unchanged Android live updates use a zero FCM time to live, so only reachable devices receive the refresh. A refresh leaves a pending state change queued. Live starts, ends, and changes retain their delivery window, and Android orders delayed messages by observation and send time. [FCM message lifespan](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan)
- A separate radar worker samples an operator receiver and stores bounded-retention, ordered positions for tracked airborne flights. It excludes explicit ground reports and only stores receiver fixes that match one current tracked leg. The radar API pages cached provider and receiver positions independently from the same database snapshot. A tail withdrawal or change of aircraft or provider instance invalidates the receiver history. The mobile app resets its local positions and cursor on the new receiver revision, including when the replacement is empty. It refreshes flight details before rendering radar for a different revision. It replaces revised provider snapshots independently. The flight map renders bundled coastlines, labels the latest observation with its source, and leaves breaks where reports are more than five minutes apart.
- The optional FAA registry ZIP supplies a model name and approximate age for current US aircraft in AeroAPI search and refresh. The provider type designator remains separate. The registry also supplies Mode S addresses for receiver matching. Plano streams only the master and model tables into a limited index at startup. [FAA registry setup](docs/SELF_HOSTING.md)
- iOS and Android keep a private cache of up to 150 tracked flights and eight recently opened details, including bounded recorded radar. A transport or server failure can show saved data for up to 72 hours. The app labels the saved time and pauses radar polling and flight actions until a fresh response arrives. The cache is bound to the current server and installation. Successful untracking removes the saved flight, and an authentication rejection clears that installation's cache. [Flighty offline mode](https://flighty.com/help/offline-mode)
- Connection suggestions use only the installation's tracked flights. Plano checks airport identity and scheduled chronology and ranks pairs with a shared private booking digest ahead of schedule matches. Opening a suggestion uses the same assessment as a manually selected pair. [Review possible connections](docs/FLIGHT_IMPORTS.md#review-possible-connections)
- A Connection Assistant monitor is an explicitly saved, installation-owned pair of tracked flights. Accepted observations on either leg trigger the same scorer used by the HTTP API, and scheduled reevaluation covers clock-driven changes. A worsening transition and its visible alert are stored together. Disabling the monitor or untracking either leg clears its pending deliveries. [Connection risk and monitoring](docs/AIRPORT_TRANSFERS.md#monitor-a-connection)
- Connection Assistant supplies official terminal maps for eight airports, secure-side directions at supported gate areas, and public transfers with screening at EWR and JFK. Built-in directions use general estimates. Operator graphs take precedence when available. [Airport maps and directions](docs/AIRPORT_TRANSFERS.md#official-maps-and-connection-directions)
- Connection gate forecasts use recent completed operations on the same flight designator and route. Verified aliases contribute one observation per flight instance, and a reported terminal restricts the historical sample to that terminal.
- One-use Friends invitations create directed relationships. Each flight grant follows the sender’s tracking state. Public pickup links expire and have independently revocable handles. [Flight sharing](docs/FLIGHT_SHARING.md)
- Passport collapses tracked aliases that share a verified provider instance. Confirmed terminal observations determine completion, and a compatible older arrival can supply missing measurements. Mobile loads up to 50 recent flights and one route segment per mapped airport pair with its lifetime totals. Older pages reuse the same flight identities and skip airport lookups.
- Optional TripIt subscriptions store encrypted feed URLs scoped to an installation. A leased worker matches dated calendar entries and commits imports only if the subscription generation still matches. The optional reservation bridge receives lookup credentials on explicit request and returns dated flight designators for user review. [Flight imports](docs/FLIGHT_IMPORTS.md)
- Every product route is available without a billing or entitlement check. External feed access, Apple signing and cloud push credentials belong to the instance operator. The self-host service can also run against explicitly labeled synthetic data for local evaluation. [Self-hosting](docs/SELF_HOSTING.md)

## Verified self-host paths

The Go test suite exercises installation isolation, outbox persistence and retries, provider wire contracts, and the aviation fixture adapters. A standalone localhost smoke test verified the health endpoint, flight lookup, tracking and database persistence after restart. A rootless Podman smoke verified the image as UID 10001 with a read-only root and mounted SQLite storage. Two successive containers served the same installation token and tracked flight. Compose configuration also validated with the explicit health check and optional credential mounts.

Live startup requires an enrollment code or an explicit private-deployment override. `plano check-config` validates deployment inputs before opening SQLite, binding a port, or contacting providers. The health command probes the running service separately and checks its Plano status and mode. A rootless smoke on the Docker-format image exercised the built-in health check, enrollment, installation isolation, and pickup links across service recreation and enrollment-code rotation. [Self-hosting](docs/SELF_HOSTING.md)

The HTTPS Compose overlay publishes only Caddy and requires enrollment in both demo and live mode. Merged Compose validation confirmed the private API port and compatibility with read-only credential mounts. A rootless loopback test with the Plano and Caddy images used a trusted local certificate and verified HTTP redirect, HTTPS health, enrollment, tracking, and a pickup link. During a simulated API outage, Caddy's error log omitted the pickup path and request headers. Public certificate issuance and phone connectivity require testing on the deployment's network. [HTTPS with Compose](docs/SELF_HOSTING.md#serve-https-with-compose)

The online backup regression test restores an installation and its tracked flight from a snapshot taken with uncheckpointed data in the live WAL. In both standalone and rootless container restore drills, a separate demo instance served the tracked flight over HTTP using the original installation token. The container drill created the backup while running with a read-only root and restored it to a fresh volume. [SQLite VACUUM INTO](https://sqlite.org/lang_vacuum.html)
